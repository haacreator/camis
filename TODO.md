# CAMIS final year project TODO

The defense should show one complete workflow: a client requests a service, a manager approves it and assigns work, staff update a task and record an interaction, the client sees current progress, and the manager gets an evidence-backed alert. The admin then exports a report and finds the same actions in the audit log. Use a fictional dataset and one project ID throughout. See the [audit](CAMIS-AUDIT.md) and [thesis revision guide](CAMIS-THESIS-REVISION.md).

## P0 Build and make the main workflow real

- [ ] Fix strict backend TypeScript errors in auth, models and Express controllers. Validate request bodies and normalize route parameters before use; add bcrypt typings. Pass the frontend/backend type checks and production builds from a clean checkout.
- [ ] Boot an isolated PostgreSQL instance and run migrations plus a deterministic seed with four roles, two distinct clients, pending and overdue work, interactions and financial records. Add setup steps, safe variable names in an example configuration, and a reset command for the isolated demo.
- [ ] Replace bundled sample data in `RoleDashboard.tsx` with the relevant calls from `src/services`. Remove personal demo details from the public bundle. Show loading, empty, stale and failure states. Wire exports to filtered API data.
- [ ] Complete the client quote form, manager approve/reject and assign screens, and staff task board/interaction form. Preserve IDs across views. Add a project timeline to the client portal with only client-visible events; keep internal notes private. Confirm whether task deliverables require files or a simpler status/link field.
- [ ] Make quote acceptance safe under repeated clicks: validate assignee role/status and dates, change pending status atomically, add unique non-null project quote reference if the business rule is one project per quote, and show the outcome in the UI. Test that one approved quote creates one project; rejected quotes create none.
- [ ] Add admin client/user lifecycle screens, active/disabled status enforcement and a role/ownership matrix. Prove that two client accounts see different data and cannot access each other's records, and that staff can change only authorized work. Use safe archival unless an agreed deletion rule requires otherwise.
- [ ] If online payment is in the defense scope, use Flutterwave sandbox. Bind references and amounts to server-stored financial records and authenticated owners; verify provider results and apply each provider transaction once. Test wrong amount, cancellation, and duplicate callback. Otherwise demo an authorized internal financial record and label online reconciliation unfinished.

## P1 Analytics automation and evidence

- [ ] Make live dashboards the decision tool: give managers an **Attention Needed** queue with reason, deadline, owner, updated time and link to the source project/task. Add date and service filters, KPI drill-down, and a visible refresh time. Start with refresh on mutation and controlled polling; state the measured refresh interval in the thesis.
- [ ] Define metric formulas and date basis before showing them: engagement = logged interactions by period/channel; quote conversion = approved / eligible submitted quotes within the same cohort; workload = open assigned tasks; completion = completed / eligible projects; collection = paid / due, grouped by agreed currency and period. Check filter boundaries and handle zero denominators. Use seeded known totals to verify exports.
- [ ] Turn the existing project health rule into scheduled and event-driven automation. On task assignment or project status change, write an in-app notification for the relevant user. On a scheduled scan, find open projects due within three days with unfinished tasks, and overdue projects; create/update an insight with rule, severity and evidence IDs. Use a unique deduplication key per recipient/source/rule and reminder window, and resolve items when conditions clear. Weekly manager digest can be generated from the same records after the inbox works.
- [ ] Add a migrated `notifications` table (recipient FK, event type, source reference, created/read times, unique dedupe key) and an `insights` table if insights need persisted history (project FK, rule, severity, evidence, status and timestamps). Build an unread badge, inbox and mark-read action. Run the job twice on the same seed and show no duplicate. Verify that one user's alert never appears in another's inbox.
- [ ] Generate audit events from the authenticated actor inside successful backend workflows. Log actor, action, target, status and server time for quote approval, task update, client lifecycle, payment and alerts. Restrict reads and avoid storing secrets. Verify that a rollback leaves no success audit and that exports do not expose session material.
- [ ] Run the defense on a fresh database. Capture a requirement-linked results table, before/after screenshots and report exports, normal-workload timings, 50-user load results, cross-browser checks, and a backup/restore exercise. Run a short supervisor/partner walkthrough if available; record actual task completion time and feedback, keeping planned claims separate.

## P2 Optional AI extension

Build **Explain this insight** on the Attention Needed queue after the rules and inbox pass. The rule engine identifies the condition and calculates all numbers. AI explains a stored insight and suggests one follow-up for a manager to approve. This directly supports the HOD's decision-making objective and works on a small demo dataset without training a predictive model.

- [ ] Add a manager/admin-only action such as `POST /api/insights/:id/explanation`. Validate access before fetching any evidence. Have the backend send approved structured fields only: risk category, days remaining, open task count and permitted source IDs. Keep keys on the backend; omit client contacts, notes, invoice details and secrets. Use fictional data for the demo.
- [ ] Ask the provider for a short explanation and suggested action in a typed response. Verify cited IDs are from the supplied evidence, reject malformed or unsupported claims, and display a deterministic template if the provider fails or is disabled. Record model/version and latency if retained. Show the original metrics beside the explanation. Manager approval is required before any action, and no message is sent automatically.
- [ ] Evaluate scripted cases (overdue, due soon, on track, missing data, unauthorized request, provider timeout). Compare AI against the plain template on factual agreement, usefulness, latency and cost. Show one example with real evidence IDs from the fictional database and a working fallback. Claim AI only after the integration and evaluation succeed.

## Decisions to take to your supervisors

Confirm whether staff may approve quotes or approval belongs to the manager/admin; whether in-app notifications satisfy communication or email and two-way messaging are required; what “real-time” means for this project; whether archived client records satisfy deletion; and whether Flutterwave or AI is required for grading. Bring the module matrix and ask them to confirm scope before adding extra screens. The highest-value additions are live role workflows, a measurable analytics queue, alerts and an audit trail.
